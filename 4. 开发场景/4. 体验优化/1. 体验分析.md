# 1. 体验分析指标

- 背景是 C 端业务线上持续有 badcase 问题反馈，如果反馈后再解决，较为后置，影响线上用户满意度，因此用户体验指标旨在量化和评估用户在使用产品时所感知体验质量的数据指标，用于监控，定位，快速解决
- 通常采用 BSR 指标，即 Bad Session Ratio，公式为 BSR = Bad Session / Session，指的是在使用产品中碰到极差体验的 PV 占比
- 不同业务场景对 Bad Session 的定义不同，以 C 端业务为例，主要从用户视角出发
  - **注重耗时**，包括 渲染耗时，关键图片加载耗时，弹出框加载耗时，下拉刷新耗时，点击响应耗时 等
  - **注重信息准确**，包括 价格不一致率（ 跳转前后页面价格不一致 ）等
  - **注重错误率**，包括 优惠卷过期率，领劵失败率，资源加载失败率，接口请求失败率 等
  - **注重结果相关性**，包括 无结果率，点击反馈（ 不相关，价格贵 等 ）率
  - **注重流畅度**
    - 因为 FPS 代表的是每秒帧数，通常用于衡量应用在一定时间内的平均帧率，但是无法捕捉 瞬时卡顿 和 帧时间波动（ 比如一帧花了 10ms，另一帧花了 100ms ）
    - 因此通常采用 丢三帧率（ 即每 s 内发现掉帧时间长于或等于 3 \* 16.67 ms 的时间占比，因为 50 ms 卡顿时，用户能明显感知 ）来评估应用的流畅度，比如 丢三帧率 为 20 %，即滑动中平均每秒有 200 ms 处于丢三帧的阻塞中
      - < 8 优秀，提升空间小
      - < 16 平均，有提升空间
      - \>= 16 一般，较大提升空间

# 2. 图片加载耗时

- 在重视图文的场景，图片优化对用户体验有显著影响，常用优化策略如下
  - HEIF 图片
    - 常见图片格式包括 jpg（ 和 jpeg 完全一致 ），png，webp，heic 和 avif
    - 对比同一张图片（ 不同图片可能压缩效果不同 ）
      - png 大小 7.1 mb，jpg 大小 1.7 mb，webp 681 kb，heic 695 kb，avif 527 kb
      - png 大小 7.7 mb，jpg 大小 702 kb，webp 305 kb，heic 149 kb，avif 239 kb
    - 但 heif 解码时间相比 jpg 略微增加，不过总体 heic 更优，已经全面迁移至 heic，用 webp 兜底，预估比 webp 节省 30% 以上带宽
    - heic 与 avif 的对比
      - 压缩后体积接近，编码速度也接近
      - 两者都遵循 HEIF 容器定义，只不过 heic 是基于 HEVC 编码，avif 是基于 AV1 编码，该两种编码策略，前者需要专利授权，而后者是开源的
      - 通过 caniuse 查看，avif 浏览器兼容率 96.19%，而 heic 兼容率仅有 14.74%（ 但实际使用还是得看开发的 app 是否存在解码 heic 或者 avif 的 sdk ）
  - 图片裁剪
    - 比如在横向容器中，展示竖图时，不需要将图片全部下发，可以裁剪后下发
    - 拓展：如何裁剪可以通过模型自动判断主体区域位置
  - 图片按需缩放
    - 如果图片在页面渲染的像素值时 48 \* 48，一般服务端会直接下发 500 \* 500 的图片，这样体积偏大，并且设备缩放过程中容易计算不精确导致模糊
    - 目前绝大多数手机、平板和电脑采用 2x 屏幕，因此通常下发 2x 图，即 96 \* 96 的图片即可
    - 需要请求图片的时候添加像素值信息，服务端按需缩放后下发
  - 域名收敛
    - 因为 http2 存在多路复用，因此可以将图片统一在一个域名下，节省 DNS 解析 和 TCP 握手 的时间（ 如果是 HTTPS 则减少了 TLS 握手时间 ）
  - 域名预连接
    - 预连接，即提前和域名建立连接，但不发送实际的业务请求，前端可以通过 \<link rel="preconnect" href="https:\/\/example.com" /> 实现
    - 如果这个连接建立后的几秒内（ 比如 Chrome 大约是 10 秒 ），浏览器没有通过它发送任何真正的请求，那么浏览器就会认为这是一次 “未使用的推测性预连接”，并主动将其关闭以释放资源
