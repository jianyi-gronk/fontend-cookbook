# 1. 离线包

## 1.1 基础使用

- 离线包 是将包括 HTML、JavaScript、CSS 等页面内静态资源打包到一个压缩包内，预先下载该离线包到本地，然后通过客户端打开，直接从本地加载离线包，从而最大程度地摆脱网络环境对 H5 页面的影响
- 每个离线包发布时，都会同步在 CDN 发布一个对应的线上版本，为了防止首次进入 app 还未下载离线包，CDN 目录结构和离线包结构一般相同
- 通常 CDN 地址会包含在离线包信息里，H5 容器会先截获静态资源请求，截获请求后，发生如下情况
  - 如果本地有资源可以满足该请求的话，H5 容器会使用本地资源
  - 如果没有可以满足请求的本地资源，H5 容器会使用线上资源

## 1.2 优化方案

- 上线 和 快速回滚
  - 可以引入新接口，用来告知客户端当前可以使用的版本白名单，客户端会 轮训，在每次冷启动 和在切后台返回时刷新接口数据（ 有较短时间的限频和缓存逻辑 ），从而可以实现以下能力
    - 发布新版本时，设置旧版本过期时间
      - 灵活控制旧版本的下线时间，如果在指定时间后，用户仍然没有更新到新版本，那么就会直接请求线上资源
      - 一般设置 2 个小时过期，就能保证大部分用户仍然可以享受到离线包的提速，也能保证不存在版本残留问题和更新不及时的问题
    - 快速下线
      - 在出现线上紧急 Bug 需要修复时，可以使用版本白名单，强制客户端走线上请求，但仍然保留本地离线资源包，从而方便后续发布新版本修复问题（ 增量发布 ）
- 虚拟域名
  - 通常需要通过 WebViewAssetLoader 创建虚拟域名（ 如 test:\/\/example.net ），将 assets 目录资源映射为网络路径，原因如下
    - 使用 file:// 协议会触发 CORS 限制
    - 防止用户看到了本地目录结构，存在安全风险
- 高低优先级
  - 离线包通常可以根据业务重要性设置不同优先级，比如让冷启动 App 的用户按照资源包优先级逐步下载到新版本
- 公共包
  - 集合公共 JS 资源，避免多份打包
- 增量包下发
  - 对每个版本的包，都会生成这个包和前 N 个版本差分计算的增量包，根据客户端当前离线包版本下载增量包
- 仅 wifi 下载
  - 节约用户流量
- 版本限制
  - 避免新资源包调用的客户端能力在旧版本不支持

# 2. 网络请求

- 启用 HTTP/2
  - 如果 HTML、CSS、JS 等资源都来自同一个域名，那么这些资源的请求可以全部复用同一个 TCP 连接，不需要为每个文件重新建立连接
- 使用 CDN 分发
  - 将静态资源部署到离用户最近的节点，降低 RTT（ 往返时延 ）
- 预操作
  - 预连接：在页面加载时，提前连接到静态资源的域名，避免在需要时才连接，导致延迟
    `<link rel="preconnect" href="https://api.example.com">`
  - 预解析：在页面加载时，提前解析静态资源的域名，避免在需要时才解析，导致延迟
    `<link rel="dns-prefetch" href="https://api.example.com">`
  - 预加载单个资源：以高优先级异步下载资源，但不会执行或应用
    ```html
    <link rel="preload" href="main.js" as="script" />
    <link rel="preload" href="style.css" as="style" />
    <link rel="preload" href="image.png" as="image" />
    ```
  - 预加载模块及其依赖树：会递归下载 app.js 中所有静态 import 的模块，适合 ES module 项目
    `<link rel="modulepreload" href="app.js">`
- 配置缓存策略
  - 主要分为 强缓存 和 协商缓存，两者的核心区别在于 是否向服务器发送请求
  - 强缓存
    - Cache-Control（ HTTP/1.1，推荐 ）
      - 常用指令
        - max-age=\<seconds\>：缓存有效期（ 相对请求时间 ），例如 Cache-Control: max-age=3600 表示 1 小时内直接使用缓存
        - no-cache：强制协商缓存（ 每次使用前向服务器验证 ）
        - no-store：禁止任何缓存（ 每次都要完整下载 ）
        - public / private：public 可被任何中间节点缓存（ 如 CDN ），private 只能被浏览器缓存
    - Expires（ HTTP/1.0，遗留 ）
      - 指定一个绝对过期时间（ GMT 格式 ），优先级低于 Cache-Control（ 若同时存在，Cache-Control 覆盖 Expires ）
  - 协商缓存
    - Last-Modified / If-Modified-Since
      - 服务器响应时返回 Last-Modified: 上次修改时间
      - 浏览器下次请求时带上 If-Modified-Since: 上次修改时间
      - 服务器比对：若资源未修改，返回 304；否则返回 200 和新资源
    - ETag / If-None-Match（ 更精确 ）
      - ETag 是资源唯一标识，通常是文件哈希
      - 浏览器下次请求时带上 If-None-Match: 旧ETag
      - 服务器比对：若一致则返回 304，否则返回 200 和新资源
      - 优先级高于 Last-Modified（ 因为 ETag 能解决时间精度不足、文件周期性修改等问题 ）

# 3. 资源压缩

## 3.1 通用压缩方案

- 开启 Brotli 或 Gzip 压缩
  - 对 HTML、CSS、JS、JSON 等文本资源进行压缩，Brotli 比 Gzip 压缩率更高
  - 具体步骤
    - 浏览器请求 HTML：客户端向服务器发送 GET /index.html
    - 服务器返回压缩后的 HTML：如果服务器配置了压缩（ 如 Content-Encoding: gzip ），它会先将 HTML 文件压缩成 .gz 格式，然后通过网络发送给浏览器
    - 浏览器自动解压：浏览器收到响应头 Content-Encoding: gzip 后，会先解压再解析 HTML
  - 但需要注意，一般图片不开启 Brotli 或 Gzip 压缩
    - 压缩效果微乎其微
      - Gzip 擅长压缩重复度高的文本，但现代的 JPEG、PNG、WebP 等图片格式，其内部算法已经做了极高效率的压缩，本身几乎不含重复信息，因此 Gzip 无法进一步有效压缩，最终体积可能变化不大
      - 由于 Gzip 压缩本身需要添加字典等开销，有时甚至会导致压缩后的文件比原图更大
    - 压缩解码耗时
      - 压缩效果不佳的同时，Gzip 还会在压缩和解压时消耗额外的 CPU 资源。这种 “用 CPU 换带宽” 的模式，对图片来说是净亏损
- Tree Shaking
  - 删除未引用的代码，减少打包体积
- 代码分割
  - 代码分割是指将打包生成的单一、庞大的 bundle 文件拆分成多个更小、更独立的 chunk（代码块）的过程
  - 其核心目的是 按需加载 或 并行加载 这些文件，从而显著减小应用的 首屏加载时间，优化性能
  - 方法 1：多入口配置
    - 可以在 `webpack.config.js` 的 `entry` 配置中，将应用的不同部分设置为多个独立的入口起点，Webpack 会为每个入口生成独立的 bundle 文件
  - 方法 2：SplitChunksPlugin
    - 用于 提取公共代码 和 分离第三方库，核心思想是将被多个入口或模块共享的代码，或者体积较大的第三方库，提取到一个单独的文件中，避免重复加载
  - 方法 3：动态导入
    - 将不同路由对应的组件拆分，访问到该路由时才加载对应代码

      ```js
      // router.js (Vue Router 示例)
      const routes = [
        {
          path: "/home",
          // 使用动态 import 语法，webpack 会将其打包成一个独立的 chunk
          component: () =>
            import(/* webpackChunkName: "home" */ "./views/Home.vue")
        },
        {
          path: "/about",
          component: () =>
            import(/* webpackChunkName: "about" */ "./views/About.vue")
        }
      ];
      ```

      - 这里的 `/* webpackChunkName: "home" */` 是一个 “魔法注释”，它可以让你自定义生成的 chunk 文件名，便于调试

    - 组件级懒加载，即可以在一个组件内部动态导入另一个组件，例如只在用户点击按钮时才加载一个庞大的图表库
      ```js
      // 在某个组件的方法中
      methods: {
        loadChart() {
          // 动态加载一个体积较大的图表库
          import(/* webpackChunkName: "chart-lib" */ 'chart.js').then(module => {
            // 使用 module 来绘制图表
            const Chart = module.default;
            new Chart(this.$refs.canvas, { /* 配置 */ });
          }).catch(err => {
            console.error('图表库加载失败', err);
          });
        }
      }
      ```

## 3.2 图片相关优化

- 雪碧图（ 减少请求次数 ）
  - 如果一个页面有上百张图片，哪怕是很小的图标，都需要经历一次请求响应过程，那么肯定会由于请求数量的增加让整个页面的加载速度降低。将大量的小图标整合到一张图，从而减少发送请求的次数，提高页面的加载速度
  - 实质就是利用背景图和背景图的位置去显示同一张图上，不同位置的图片，进而在引入一张图的前提下，显示不同图片
  - 但是当整合图片比较大时，一次加载比较慢，随着字体图片，base64 等的流行，该技术渐渐使用的变少了
- base64（ 减少请求次数 ）
  - 直接把图片通过 base64 编码，然后放入 css 文件中，可以减少请求次数
  - 但是编码后大小大约比原始值扩大了 33%，如果图片过大，会使 css 文件过大，一般小于 10k 才会用 base64 编码
- 懒加载
  - 原生方法
    - 通过 img 的 loading="lazy" 属性，告诉浏览器延迟加载图片，直到图片滚动到接近视口时才自动加载，零 JS 成本，浏览器自动处理（ 默认值为 eager 时，立即加载图像，不管它是否在可视视口 ）
    - 兼容性问题：部分旧浏览器（ 如 IE、iOS Safari < 15.4 ）不支持
    - 示例：`<img src="real-image.jpg" loading="lazy" alt="...">`，此时浏览器不会立即请求 real-image.jpg，而是在用户滚动到该图片附近时才开始下载
  - 通过 Intersection Observer API
    - 通常用一个低分辨率占位图或纯色背景作为 src，真正的图片地址放在自定义 data-src 属性中
      `<img class="lazy" src="placeholder.svg" data-src="real-image.jpg" alt="产品图">`
    - JavaScript 实现

      ```js
      // 获取所有需要懒加载的图片
      const lazyImages = document.querySelectorAll("img.lazy");

      // 创建 Intersection Observer 实例
      const observer = new IntersectionObserver(
        (entries, observer) => {
          entries.forEach((entry) => {
            if (entry.isIntersecting) {
              const img = entry.target;
              const src = img.dataset.src;
              if (src) {
                img.src = src;
                // 图片加载完成后移除观察
                img.onload = () => img.classList.add("loaded");
                img.removeAttribute("data-src");
              }
              observer.unobserve(img); // 停止观察该图片
            }
          });
        },
        {
          rootMargin: "0px 0px 100px 0px", // 提前 100px 开始加载（视口底部下方）
          threshold: 0.01 // 元素出现 1% 时触发
        }
      );

      // 开始观察每一张图片
      lazyImages.forEach((img) => observer.observe(img));
      ```

- 选择像素合适图片
  - 通过 srcset 属性，提供一组候选图片及其各自的宽度或像素密度描述，供浏览器选择

    ```html
    <img
      srcset="image-400w.jpg, image-800w.jpg 800w, image-1200w.jpg 1200w"
      src="fallback.jpg"
    />
    ```

    - 400w、800w 是宽度描述符（ 实际图片的像素宽度 ），也可以用像素密度描述符：1x、2x 等，如果没有指定则默认是 1x
    - 浏览器会根据当前视口宽度、设备像素比等，从列表中选择最合适的图片
    - 如果是 600w，会选取第一个大于 600w 的图片，此时是 800w

- 图片压缩
  - Webpack 主流的图片压缩插件，如 `image-webpack-loader` 和 `image-minimizer-webpack-plugin`，其底层都依赖于 imagemin 库
  - imagemin 就像一个 “调度中心”，它本身不直接处理图片，而是根据不同图片格式调用相应的专用插件和底层工具来执行压缩
  - 以 `image-webpack-loader` 举例

    ```js
    {
      loader: 'image-webpack-loader',
      options: {
        // 生产环境才启用压缩，开发环境禁用
        disable: process.env.NODE_ENV === 'development',
        // 配置各格式压缩选项
        mozjpeg: { progressive: true, quality: 65 },
        optipng: { enabled: false },
        pngquant: { quality: [0.65, 0.90], speed: 4 },
        gifsicle: { interlaced: false },
        // 启用 WebP 转换并设置质量，一般建议 75-80
        webp: { quality: 75 },
      },
    },
    ```

    - 会根据 待处理图片的文件扩展名，自动选择对应的压缩工具
      - `.jpg` / `.jpeg` 文件：自动应用 `mozjpeg` 选项
      - `.png` 文件：自动应用 `pngquant` 和 `optipng` 选项
      - `.gif` 文件：自动应用 `gifsicle` 选项
      - `.jpg` / `.jpeg` / `.png` 文件：自动应用 `webp` 选项， 将图片格式转换为 webp
