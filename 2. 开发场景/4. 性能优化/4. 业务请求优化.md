# 1. SSE（ Server-Sent Events，服务器推送事件 ）

- 可以通过 SSE 拆分业务数据，先下发最核心的业务数据，**减少请求数据大小**
- 虽然 WebSocket 是双向全双工，也可以实现服务端主动推送数据，但除非场景强依赖双向，否则一般不使用，主要原因在实现成本上
  - 协议：SSE 基于 HTTP/1.1 或 HTTP/2，而 WebSocket 基于独立的 `ws://` / `wss://` 协议
  - 自动重连：SSE 浏览器会自动尝试重连，而 WebSocket 需要手动实现
  - 连接开销：SSE 复用 HTTP 连接，轻量，连接开销低，WebSocket 需要维护心跳，连接开销较高
  - 消息 ID：SSE 支持 id 字段，断线重连后可恢复未接收消息，WebSocket 无内置，需自行实现
- 具体使用
  ```js
  const source = new EventSource("/api/stream");
  source.onmessage = (event) => {
    console.log("收到数据:", event.data);
  };
  // 监听自定义事件（ 服务端可发送 event: userlogin ）
  source.addEventListener("userlogin", (event) => {
    console.log("用户登录:", event.data);
  });
  source.onerror = (err) => {
    console.error("连接错误");
  };
  // 主动关闭
  source.close();
  ```
- 和普通 http 的区别是，在请求头上有 `Accept: text/event-stream`，在响应头上有 `Content-Type: text/event-stream`

# 2. SSR（ Server-Side Rendering，服务端渲染 ）

- 将业务数据获取和首屏渲染移至服务端，**减少首屏业务请求次数**
- 传统 CSR（ 客户端渲染 ）流程
  - 浏览器请求 HTML -> 下载 JS -> 执行 JS -> 发起业务请求 -> 获取数据后渲染页面
- SSR 流程
  - 服务端直接获取业务数据（ 如调用数据库、微服务 ） -> 将数据注入 HTML 模板 -> 返回完整的 HTML（ 包含首屏内容 ） -> 浏览器直接显示内容 -> 下载并执行 JS 进行 “水合”，绑定事件，使页面可交互
- 优势
  - SEO 友好：搜索引擎爬虫能直接获取完整 HTML 内容，无需执行 JavaScript，利于收录和排名
  - 首屏加载更快：用户第一时间看到有内容的页面，减少了白屏时间和 FCP（首次内容绘制）
  - 弱网/低端设备友好：不依赖下载和解析大量 JS，降低对客户端性能的要求
  - 减少客户端请求：关键数据已在服务端获取并内嵌在 HTML 中，避免了首屏阶段额外的 AJAX 请求
- 缺点
  - 服务器压力增大：每个请求都需要在服务端执行渲染逻辑，对 CPU 和内存消耗较高，并发能力有限
  - TTFB 可能增加：服务端需等待数据接口返回才能生成 HTML，可能导致首字节时间变长
  - 开发复杂度高：需处理服务端与客户端环境差异（ 如 window 不存在、生命周期钩子差异 ），代码需同构
  - 缓存策略复杂：动态内容难以利用 CDN 缓存，需结合页面级缓存或分布式存储
  - 水合成本：客户端仍需加载 JS 并重新渲染，可能产生短暂交互延迟（ 如 FID ）
