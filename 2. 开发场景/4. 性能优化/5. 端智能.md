# 1. 端智能

- 背景
  - 端智能相对于云智能，在 **数据获取的实时性**（ 避免数据通信耗时 ）和 **数据使用的安全性**（ 安全隐私合规风险 ）上具备很大优势
  - 且随着移动端设备发展，**性能和存储能力提升**，端具备一定空闲算力空间，有机会缓解服务器压力
- 核心思想
  - 基于端侧丰富的实时用户数据，调整端侧和云侧的分工，给予端侧自主决策的能力，实现效果更好的协同效应，从而实时感应，分析 和 响应用户状态或兴趣的变化
  - 端模型需要轻量化（ 避免对移动端带来压力 ），决策需敏捷（ 应对高频次运算 ），比如使用 xgb，大概 100 多个特征，体积 1mb 左右，耗时 10ms 左右
- 使用场景
  - **预加载 和 预请求**
    - 是非常重要的性能优化手段，但直接预测在命中率不高的场景，会造成严重的资源浪费或导致无效 qps 涨幅
    - 可以根据用户行为，点击，成交概率等进行预测，按照 预测结果 进行 链路数据预请求 和 资源预加载
  - **重排序**
    - 在排序场景很多的场景，比如店铺顺序，商品顺序，标签顺序等
    - 可以拿到用户最新行为，根据端智能模型策略，对还未展示的卡片进行 重排序
  - **千人千面**
    - 通过实时的用户操作行为，偏好，环境，设备等信息，进行 端智能分析，从而判断用户的及时性偏好，进行动态 UI 交互展示或者变化，从而更加针对用户进行 UI 层面的 千人千面
- 各环节分工
  - 前端团队：负责根据业务数据组装特征（ 这一步其实可以放在客户端做，只是因为根据实验结果，特征需要频繁迭代，而客户端更新需要走发布流程 ）
  - 客户端团队：提供基础能力和框架，负责接受前端传递的特征数据并调用算法包，native 处理链路需要具有通用性，可兼容不同卡片的特征数据，触发不同的后续链路预加载
  - 算法团队：提供算法包，但没有业务研发了解各项指标在业务场景的定义以及重要性

# 2. 特征设计

- 总共大概 100 多个，业务数据只有 20 多个
- 基础特征（ 最近 n 小时 / 最近 n 次 内 ）
  - 用户特征
    - 进入途径，个人点击 pv，个人曝光 pv，提交订单数 等
  - 机型特征
    - 网络，内存，机型打分（ 云端特征 ）等
- 业务数据（ 以 poi 场景举例 ）
  - 不同卡片的数据不同，因此特征也不同，大概包括
    - 卡片排名，poi 名，所属行业，地理位置，距离，7 天累计销量，30 天累计销量，poi 评分，评分，评论数，是否直播中，是否营业中，是否广告，poi 排名信息，用户相关信息（ 浏览过 ），销售量，营销标签（ 免预约，过期退 等 ）等
- 用户画像特征
  - 例如 近 n 天活跃内的天数，教育水平，是否高知用户，近 n 天被举报量，近 n 天客诉量 等
  - 云端下发的特征，会根据 3d/7d/14d/30d 等 时间维度进行更新
  - 如果用户切换账号，需要重新获取用户画像特征

# 3. 实现方案

- 训练过程
  - 通常定义特征后，需要上报收集 14 ～ 30 天特征数据（ 因为很多特征是通过处理得到 ），输入给云端进行训练模型
- 业务流程
  - 卡片加载完，监听客户端事件（ 通知前端收集业务特征并传给客户端，因为未上屏的数据信息不需要给客户端 ）
  - 客户端会收集所有屏幕上展示的卡片列表的所有特征，并添加上 基础特征 和 云端用户画像特征，统一传给算法包（ 因为上下 poi 信息也会影响用户行为 ），如果是首次运行会去云端获取算法包
  - 因为后续跳转链路存在三种，因此构建了三个不同的模型分别进行预测跳转概率，客户端进行收集，最终构建一个 list，对应每个卡片对应三种链路是否需要预加载
- 最重要的两个指标
  - 召回率
    - （ 预测为 真 且 实际为 真 ）/（ 实际为 真 ）的比例
    - 可以体现为端智能对性能的优化大不大
  - 准确率
    - （ 预测为 真 且 实际为 真 ）/（ 预测为 真 ）的比例
    - 体现为端智能对 qps 的压力大不大
- 模型通常会训练给出一个合适的阈值，比如 0.5 等，可以在此基础上，基于 召回率 和 准确率 进行微调
  - 提高阈值，通常会导致 准确率上升，召回率下降
  - 降低阈值，通常会导致 准确率下降，召回率上升
- 准确率不高的时候，会导致下游 qps 压力过大，限制模型的使用场景，比如准确率较低时
  - 只能选取页面中点击概率最高（ 得超过阈值 ）的卡片进行预请求和加载
  - 只能选取每个商家中点击概率最高（ 得超过阈值 ）的商品进行预请求和加载

# 4. 优化方向

## 4.1 减小算法包体积

- 目前每个跳转场景都存在一个算法包 1mb+，搜索结果页目前接入 3 个跳转场景对应 3 个算法包，可能后续还有其他跳转链路需要接入，不可能每次都线形增加体积
- 可以抽取公共算法部分，再分场景做差异化处理，大概从 3mb+ -> 1mb+

## 4.2 完善基础框架

- 细化基础框架
  - 所有卡片使用相同的业务特征 -> 每种卡片使用不同的业务特征 -> 每种卡片的每种行业（ 比如相比美食行业，酒旅更关注是否干净 ）
- 扩展使用场景
  - 前置链路 -> 业务场景 -> 后续链路
  - 不仅可以在业务场景跳转到后续链路的场景使用，前置链路跳转的时候也能接入端智能，不过需要前置链路训练并接入对应算法包

## 4.3 优化特征

- 需要结合 业务 和 实验结果 分析，不断修改特征，优化模型预测准召率（ 准确率 + 召回率 ），优化方案如下
- 业务分析
  - 比如 商品列表是 全部竖列展示 还是 横滑展示，这个会结合商品顺序影响点击商品操作
- 数据转换
  - 比如字符串转数字，提取 5.6折，1万，10k，¥10，五十 等
  - 模型对这种 字符串类型特征 的处理远远不如 数值类型特征
- 其他可以考虑的操作
  - 添加性能特征（ 以 poi 场景举例 ）
    - 比如 图片 和 卡片 等 加载时间（ 在重信息的场景，用户是否会优先关注加载图片快的 poi ）
  - 添加标签是否展示
    - 展示出来的元素更影响用户点击，不应该直接将服务端下发的标签传给模型，应该再做一层区分，“标签下发未展示” 和 “标签下发且展示”
  - 尽量避免字符串特征
    - 比如目前是直接将 “xxx 地区 xxx 榜单 xxx 名”，可以额外添加 3 个特征，比如 “什么级别榜单”（ 市，区，街道 等 ），“什么榜单”（ 好评，常去 等 ），“第几位” 等
    - 因为直接全部传入模型不易从包含了 3 个特征的混合特征去学习到有用信息

## 4.4 其优化方案

- **削峰填谷**
  - 预请求场景，可以在午晚高峰提高决策阈值，降低服务端 qps 压力
- **低点击率**
  - 建设画像，判断是否是 高活用户 或 高活业务信息，可以剔除很大比例不必要预测
    - 用户纬度画像：过往该用户在该场景的 总次数 和 频率 较高
    - 业务纬度画像：过往该业务信息（ 比如 商品 等 ）被用户点击的 总次数 和 频率 较高
- **多时机预测**
  - 比如视频场景，直接预测可能会导致模型遗漏 点赞，评论，关注 等关键事件（ 比如点赞后用户会有较大评论概率等 ），可以在停留 n 秒后，或者在各种操作的时机开始预测
